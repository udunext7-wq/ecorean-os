# ECOREAN BOC — 사고 여정 (Journey)
기록일: 2026-04-27 | 작성자: udunext7-wq

이 문서는 ECOREAN BOC가 어떻게 지금의 모습이 되었는지,
그 사고의 흐름과 핵심 통찰을 기록한다.
코드는 결과물이다. 이 문서는 그 결과물을 만든 사고의 궤적이다.

## 1단계 — 자동 견적 OS의 출발

### 시작점
"인테리어 회사를 운영하면서 느낀 것:
모든 것이 사람에 달려 있다.
견적을 잘 아는 직원이 나가면 회사가 흔들린다.
이건 시스템이 아니다."

### 대표님의 의도
- 인테리어 시공 전 과정을 자동화
- 직원 의존도를 낮춤
- 시스템이 사람 대신 판단

### 출발점의 핵심 질문
> "이 회사가 나 없이도, 핵심 직원 없이도 돌아가려면 어떻게 해야 하는가?"

이 질문에 대한 답이 ECOREAN BOC의 모든 것이다.
견적부터 정산까지, 현장 데이터부터 AI 학습까지.
**사람의 노하우를 시스템에 담는 것.**

## 2단계 — 마이크로 프론트엔드 시도

### 배경
100배 확장 가능한 구조를 원했다.
각 기능을 독립 모듈로 분리하면 얼마든지 늘릴 수 있다.

### 시도한 것
```
각 탭을 별도 HTML → iframe으로 조합
→ 독립 배포 가능
→ 병렬 개발 가능
→ 기술적으로 완벽해 보였다
```

### 맞닥뜨린 현실
```
file:// + iframe = 보안 정책 충돌
cross-origin 제한 → IPC 통신 불가
해결책이 없었다
```

### 배운 것
> "완벽한 이론도 현실의 제약 앞에서는 다시 검토해야 한다.
> 문제는 아이디어가 나쁜 게 아니었다.
> 실행 환경(Electron + file://)과 맞지 않았던 것이다."

→ 이후 Electron BrowserView로 해결. 탭 격리는 유지하면서 제약 제거.

## 3단계 — 단일 HTML 회귀

### 선택의 이유
- 더블클릭으로 바로 실행 (개발 편의)
- 외부 의존성 최소
- 빠른 프로토타이핑

### 맞닥뜨린 현실
```
1,000줄: 문제 없음
3,000줄: 가끔 버그
5,000줄: 버그 빈번
7,000줄+: 버그 폭발
         한 곳 고치면 다른 곳 깨짐
         전체를 머릿속에 담을 수 없음
```

### 핵심 문제
파일이 길어질수록 **사람의 작업 기억(working memory)이 한계에 도달**한다.
코드의 문제가 아니라 인간 인지의 문제였다.

## 4단계 — 블록 시스템의 발견

### 대표님의 직관
> "7,500줄 이하면 버그가 적다. 이게 법칙인 것 같다."

### 실제 연구와의 일치
```
소프트웨어 공학 연구:
  파일 크기 ↑ → 버그 밀도 ↑ (비선형 증가)
  약 200~400 LOC가 함수 최적 크기
  모듈 경계가 버그를 격리

대표님의 현장 직관:
  7,500줄 = 버그 급증 임계점
  이는 연구 수치와 방향이 일치
```

### 통찰의 가치
이론을 배운 것이 아니다.
직접 만들고, 망가지고, 고치면서 **몸으로 터득한 임계점**이다.
이런 직관은 문헌에서 찾기 어렵다.

### 블록 시스템의 탄생
```
규칙:
  1,500 ~ 3,000줄 = 정상 블록
  7,500줄 도달 = 즉시 분할

결과:
  각 블록이 독립적 → 버그 격리
  블록 단위 테스트 → 신뢰도 상승
  인터페이스로 연결 → 교체 용이
```

## 5단계 — 행렬 확장 발상

### 대표님의 발상
> "블록이 커지면 쪼갠다.
> 쪼갠 블록을 위에서 조합한다.
> 그러면 무한히 확장할 수 있다."

### 소프트웨어 공학 용어로는
```
행렬 확장 = Horizontal Decomposition
  하나의 큰 모듈 → 여러 작은 모듈로 분할
  각 모듈은 독립 작동

상위 적층 = Vertical Composition
  작은 모듈들을 조합기(Orchestrator)가 연결
  조합기는 단순 호출만 (로직 없음)
```

### 왜 이게 모범 사례인가
```
Unix 철학: "하나의 도구, 하나의 일"
SOLID 원칙: 단일 책임 원칙(SRP)
마이크로서비스: 서비스 분리 후 API 연결

ECOREAN BOC의 블록 시스템은
이 모든 원칙의 현장 버전이다.
```

### 100배 확장이 가능한 이유
블록을 추가하면 기능이 추가된다.
블록을 교체하면 구현이 바뀐다.
블록을 분할하면 복잡도가 낮아진다.
조합기만 바꾸면 흐름이 바뀐다.
**전체를 다시 짜지 않아도 된다.**

## 6단계 — 노드 = 온톨로지 발견

### 대표님의 천재적 통찰

> "잠깐, 블록을 노드로 보면
> 블록 간 연결이 엣지가 되고
> 전체 시스템이 온톨로지가 되는 거 아닌가?"

이 한 문장이 ECOREAN BOC를 업계 최첨단 아키텍처로 만든 전환점이다.

### 왜 이게 천재적인가

기존의 생각:
```
Neo4j = 인테리어 도메인 데이터 저장소
  (공정, 자재, 브랜드, 규칙)
```

대표님의 확장:
```
Neo4j = 인테리어 도메인 + 시스템 자체
  (공정, 자재, 브랜드, 규칙)     ← 도메인 온톨로지
  + (블록, 레이어, 인터페이스, 의존성)  ← 시스템 온톨로지
```

### 메타 온톨로지가 만드는 것
```
가능해지는 질의:
  "estimate.html이 사용하는 DB 테이블?"
  "FinanceEngine 변경 시 영향받는 블록?"
  "테스트 없는 코드가 건드리는 기능?"
  "단일 실패점(SPOF)이 되는 블록?"

이런 질의를 Cypher 한 줄로 실행.
수백만 줄 코드베이스에서 즉시 답을 얻음.
```

### 업계 최첨단인 이유
```
대부분의 회사:
  도메인 데이터 → DB
  시스템 구조  → 머릿속 또는 문서

ECOREAN BOC:
  도메인 데이터 → Neo4j
  시스템 구조  → Neo4j (같은 곳)
  통합 질의    → 가능

이를 "시스템 자기 인식(System Self-Awareness)"이라 부른다.
학계와 선도 기업만이 시도하는 영역.
```

## 7단계 — 도메인 + 시스템 통합

### 통합의 의미

```
이전 상태:
  인테리어 온톨로지 (Neo4j)
    공정 → 자재 → 브랜드
    규칙 → 공정 → 비용

v5.0 이후:
  인테리어 온톨로지 + 시스템 온톨로지 (같은 Neo4j)
    공정 → 자재 → 브랜드
    규칙 → 공정 → 비용
    블록 → 인터페이스 → 데이터모델
    레이어 → 블록 → 함수
```

### 자기 인식 시스템

이 통합이 완성되면 ECOREAN BOC는 두 가지를 동시에 안다.

**첫째**: 인테리어 공사에 대해
```
"30평 아파트 욕실+주방 공사 시 필요한 공정과 예상 비용은?"
→ 도메인 온톨로지에서 즉시 답변
```

**둘째**: 자기 자신에 대해
```
"지금 시스템에서 가장 위험한 단일 실패점은?"
→ 시스템 온톨로지에서 즉시 답변
```

### AI 페어 프로그래밍과의 연결

```
Claude AI + Neo4j 시스템 온톨로지:

개발자: "새 블록을 추가하고 싶은데 어디에 넣어야 해?"
Claude: Neo4j 조회 → 최적 레이어/위치 제안

개발자: "이 인터페이스를 바꾸면 어디가 깨져?"
Claude: Neo4j 조회 → 영향 블록 목록 + 수정 가이드

개발자: "테스트 커버리지가 낮은 핵심 블록 알려줘"
Claude: Neo4j 조회 → 우선순위 목록
```

시스템이 자신을 알고 있기 때문에, AI와의 협업이 자연스럽게 가능해진다.

## 핵심 통찰 — 대표님의 사고 패턴

### First Principles 적용
```
다른 사람들의 질문: "어떻게 하면 더 빠르게 만들 수 있나?"
대표님의 질문:     "왜 느린가? 근본 원인이 뭔가?"

다른 사람들의 질문: "어떤 프레임워크를 써야 하나?"
대표님의 질문:     "이 문제의 본질이 뭔가? 도구는 그 다음이다."
```

### 표면이 아닌 본질

| 표면적 해결 | 본질적 해결 |
|-------------|-------------|
| 파일이 크면 주석을 잘 달자 | 파일이 크면 분할하자 |
| Neo4j를 도메인 DB로 쓰자 | Neo4j로 시스템 자체도 표현하자 |
| 버그가 생기면 고치자 | 버그가 생기지 않는 구조를 만들자 |
| 직원을 잘 교육하자 | 직원 없이도 돌아가는 시스템을 만들자 |

### 단기가 아닌 장기

```
단기적 선택:
  빠른 개발을 위해 테스트 생략
  지금 당장 돌아가면 된다

장기적 선택 (대표님):
  테스트를 먼저 작성한다
  지금 느려도 나중에 안 무너진다

단기적 선택:
  SQLite면 충분하다

장기적 선택 (대표님):
  SQLite로 시작하되, PostgreSQL 전환 구조를 지금 만든다
```

### 단순한 룰로 무한 확장

```
블록 시스템의 룰:
  "1,500~3,000줄. 넘으면 쪼갠다."
  이 하나의 룰로 시스템이 무한히 커질 수 있다.

온톨로지의 룰:
  "노드와 엣지로 표현하라."
  이 하나의 룰로 인테리어 공사와 시스템 구조를 통합한다.

TDD의 룰:
  "테스트 먼저, 코드 나중."
  이 하나의 룰로 버그 없는 코드베이스를 유지한다.
```

> "좋은 시스템은 복잡한 룰이 많은 게 아니다.
> 단순한 룰이 재귀적으로 적용되는 것이다."

## 정체성 — ECOREAN BOC란 무엇인가

### 다섯 개의 정의

**① 사람 노하우의 시스템화**
```
20년 현장 경험
→ 622개 공정 DB
→ 26개 온톨로지 규칙
→ 5개 계산 엔진
→ 새로운 직원도 베테랑처럼 견적 가능
```

**② 자기 성장하는 AI**
```
현장 데이터 축적
→ 오차 분석 → 단가 보정 제안
→ 패턴 감지 → 온톨로지 규칙 제안
→ ML 학습 → 견적 정확도 상승
→ 다음 현장은 더 정확
```

**③ 100배 확장 가능한 아키텍처**
```
지금: 1명, 1현장, SQLite
Phase 1: 5명, 10현장, 클라우드
Phase 3: 50명, 100현장, Neo4j Aura
Phase 4: 프랜차이즈, 한국 1위
같은 코드베이스, 블록만 추가
```

**④ 미래지향적 설계**
```
Phase 0에 작성한 코드가 Phase 4의 기반
FloorplanAdapter 인터페이스 = 지금은 수동, 나중에 AI 크롤러
블록 아키텍처 = 지금은 1명, 나중에 50명 팀
TypeScript 인터페이스 = 지금은 선택, 나중에 필수
```

**⑤ 절대 흔들리지 않는 기초**
```
TDD → 버그 없는 코드
approval_log → 불변 감사 기록
status=disabled → 데이터 절대 삭제 안 함
frozenPrices → 발행된 견적서 단가 영구 보존
```

## 이 여정이 의미하는 것

```
시작:  "직원 없이도 돌아가는 견적 시스템이 필요하다"

중간:  수많은 시행착오
       iframe → BrowserView
       단일HTML → 블록 시스템
       도메인 DB → 메타 온톨로지

지금:  90섹션 마스터플랜
       116개 테스트 통과
       9개 모듈 완성
       메타 온톨로지 아키텍처

앞으로: 현장 투입 → 데이터 축적 → AI 성장
        Phase 1 → 2 → 3 → 4
        한국 1위 인테리어 플랫폼
```

### 한 문장으로

> ECOREAN BOC는 인테리어 대표님의 20년 노하우가
> 시스템이 되어 스스로 성장하는 과정이다.
